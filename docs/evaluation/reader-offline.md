# M1 — Reader, Offline Storage, and PWA Evaluation

The reader has reusable EPUB/KOReader position logic, but its storage, delivery, lifecycle, and content-isolation mechanisms are not a safe foundation to port unchanged into React. Reliable offline synchronization requires an additive server contract; a browser-only queue rewrite cannot provide deduplication or protect newer KOReader progress.

**Status:** evaluation, not implementation approval. Findings below are confirmed by source inspection unless marked **proposal**, **risk**, or **unverified**. The target architecture and policy alternatives require user approval. This report does not complete M1 runtime or physical-device gates.

### Service-worker and PWA behavior

- Cache policy: cache-first plus background refresh for `/local`, `/reader`, manifest, assets, book files/covers; cache-only fonts; network-first reader progress with fallback only on thrown fetch failures; all other GETs fall back to `/local` only on network rejection (`assets/sw.js:37`–`assets/sw.js:56`, `assets/sw.js:132`–`assets/sw.js:172`). The fallback is not restricted to navigation: failed JSON/image/other GETs can receive HTML. Cross-origin GETs are not explicitly excluded.
- Reading/downloading a server file can implicitly cache it; there is no explicit “download complete” record. SW listing checks file and progress URL presence, not EPUB integrity, content type, account, version, or a completed `cache.put` acknowledgement (`assets/sw.js:185`–`assets/sw.js:226`). A cover is optional in that check.
- `updateCache` starts but does not await `cache.put`; cache-first refresh is not extended with `event.waitUntil`. Cache failure may be unreported or worker termination may interrupt work. Network errors fall back, but HTTP auth/errors do not (`assets/sw.js:109`–`assets/sw.js:126`, `assets/sw.js:163`–`assets/sw.js:171`). Redirected login HTML with final 200 can be cached under an EPUB/progress URL. Expired-session progress can replace the last usable cached JSON (`api/auth.go:115`–`api/auth.go:129`).
- Install uses all-or-nothing `cache.addAll` for the listed shell/assets. There is no activate cleanup, explicit waiting-worker/user update protocol, `skipWaiting`, or `clients.claim` (`assets/sw.js:245`–`assets/sw.js:265`). Both general page scripts and reader/local pages load replay code (`assets/reader/index.htm:29`–`assets/reader/index.htm:31`; `assets/local/index.htm:36`–`assets/local/index.htm:38`).
- Manifest has name/short name, standalone display, `/` scope/start URL, one 512px `any` icon, and no explicit `id`, background color, maskable icon, or shortcuts (`assets/manifest.json:1`–`assets/manifest.json:17`). Current inferred identity/start URL must be considered before changing install identity; legacy browser data being disposable does not make duplicate installation or broken home-screen launch desirable.

## 2. Compatibility contracts: document identity, positions, and units

### Document identity is not the URL fragment or a full-file hash

1. Server document IDs use KOReader-style **partial MD5**, while `documents.md5` stores a separate full-file MD5 (`utils/utils.go:12`–`utils/utils.go:44`, `utils/utils.go:58`–`utils/utils.go:76`; `metadata/metadata.go:100`–`metadata/metadata.go:120`; `api/app-routes.go:511`–`api/app-routes.go:516`). Preserve existing IDs, row relationships, and bytes/files; React must not recalculate IDs from metadata, filenames, a new content hash, or CFI.
2. Current Go sampling uses 1024-byte chunks at offset zero then `1024 << (2*i)` for i=0..10, stopping before appending a short chunk when `ReadAt` returns EOF. Plugin Lua sampling reads available sample bytes and has its own bit-shift handling (`client/syncninja.koplugin/main.lua:1065`–`client/syncninja.koplugin/main.lua:1091`). **Risk:** short-file/tail behavior is not proven identical by the single existing EPUB vector. Do not “fix” either algorithm or rewrite historical IDs as part of frontend extraction. Add fixtures spanning empty/short/exact-boundary/partial-tail/multi-offset files and cross-check actual KOReader behavior before any future algorithm change.
3. Local-only IDs are random, not partial MD5 (`assets/local/index.js:114`–`assets/local/index.js:123`). Namespace them as local resources; a 32-character appearance does not make them server documents. Promotion/upload, if offered, needs an explicit mapping to the server-returned identity; never replay local IDs into KO endpoints. Keep an optional strong byte digest/version for integrity separate from protocol identity. Partial MD5 is not a security/content-integrity guarantee.
4. `/reader#id=…&type=…` is route selection; the fragment is not a reading position. **Proposal:** keep externally useful existing server reader links resolving to the new reader without preserving old browser keys or implementing old local-ID migration. Validate route type/ID, missing record, and unsupported content before opening.

### Stored position is a KOReader path, not a CFI

- Writer maps the current CFI spine base to one-based `/body/DocFragment[n]/body/...`, walks elements toward BODY, skips text-node precision, skips anchor parents, and calculates tag indices among descendants (`assets/reader/index.js:1017`–`assets/reader/index.js:1087`). Stored output is element-level and potentially lossy; do not promise character-exact round trips today.
- Reader accepts that DocFragment prefix, loads the spine section, prefers rendered section DOM, strips trailing `.digits` and `/text()[n]`, evaluates namespace-adjusted XPath, and falls back to descendant CSS selection to accommodate omitted anchors. Bare-section CFI receives an extra `0` workaround (`assets/reader/index.js:1094`–`assets/reader/index.js:1202`). A KO example `…/h1/img.0` need not include the actual intermediate anchor. These are external compatibility requirements to test, not a reason to scatter parsing into UI components.
- **Risks:** invalid/out-of-range fragment can dereference a missing spine item; missing element can reach `cfiFromElement`; malformed selector/XPath can throw; nested anchors/repeated descendants can map to the wrong element; text offsets are discarded; `getXPathFromCFI` uses the first rendition content rather than explicitly matching the CFI section. Book revision changes can make a once-valid path wrong. No typed unsupported-position result exists.
- **Proposal:** a position codec owns validated `KOPosition ↔ engine location` conversion and format/version metadata. Keep the original opaque KO path if conversion fails; show “saved location unavailable,” offer start/chapter fallback, and do not publish the fallback as new progress until intentional navigation. CFIs may be auxiliary browser-local precision, never a silent replacement for server `progress`. Require stable spine identity, deterministic element mapping, and documented precision for round trips. Preserve position across reflow, not page number.

Refresh occurs through `CacheTempTables`, not inside the progress handler (`database/manager.go:141`–`database/manager.go:157`; `api/ko-routes.go:80`–`api/ko-routes.go:128`). The synthetic probe confirms the progress-only gap. A separate static defect further undermines freshness: the scheduler creates one five-minute-deadline context before a fifteen-minute ticker, then reuses it for every refresh (`server/server.go:54`–`server/server.go:61`, `server/server.go:87`–`server/server.go:92`); scheduled SQL calls receive an already-expired context. This was not runtime-tested and is not changed here. **Proposal:** new web reads expose authoritative progress separately from analytics freshness, while KO field shape and persistent historical data remain intact.

## 3. Confirmed synchronization hazards and schema constraints

### Browser loss/race paths

1. **HTTP error is treated as delivered.** Fetch resolves on HTTP 4xx/5xx. Both reader flush methods and general replay merely parse JSON/log; replay then deletes keys. KO middleware returns JSON 401, so this is a concrete source-level loss path, not just an HTML-redirect concern (`assets/index.js:18`–`assets/index.js:69`; `assets/reader/index.js:876`–`assets/reader/index.js:950`; `api/auth.go:70`–`api/auth.go:78`). HTML causes parse rejection but is not a reliable error policy.
2. **Not durable before sending.** Events go directly to network; IndexedDB writes happen only in `.catch`. Process termination during fetch/catch can lose them. Success response loss can enqueue an already-committed event for duplicate credit (`assets/reader/index.js:849`–`assets/reader/index.js:872`, `assets/reader/index.js:928`–`assets/reader/index.js:933`).
3. **Delete-after-send races.** General replay reads a snapshot then deletes the entire progress key/activity envelope, even if the reader or another tab appended/replaced it meanwhile. Concurrent replay can submit the same activities twice. New pending activity can be lost in get/append/set as well (`assets/index.js:12`–`assets/index.js:37`; `assets/reader/index.js:862`–`assets/reader/index.js:870`). A successful direct progress write does not necessarily clear an older queued value, so an old queued position can overlay/replay later.
4. **No account boundary.** Cookie identity at send time selects server user, while queues/cache/preferences do not record that identity. Account B can receive account A's queued progress/activity; cached metadata can expose A's reading state (`assets/index.js:41`–`assets/index.js:69`; `assets/reader/index.js:1332`–`assets/reader/index.js:1344`; `api/auth.go:52`–`api/auth.go:63`).
5. **No serialized navigation/checkpoint lifecycle.** Page methods are async but inputs are not globally serialized; TOC calls rendition directly; no visibility/pagehide finalization, periodic durable checkpoint, or disposal exists (`assets/reader/index.js:110`–`assets/reader/index.js:113`, `assets/reader/index.js:746`–`assets/reader/index.js:780`, `assets/reader/index.js:1347`). Abrupt termination cannot be solved by relying on an unload fetch.

### What the server actually stores

- `activity.id` is a server autoincrement key. There is **no client event key, unique interval constraint, or receipt table**; `AddActivity` always inserts (`database/schema.sql:93`–`database/schema.sql:109`; `database/query.sql:1`–`database/query.sql:12`). KO adds an entire batch in one transaction, then returns only `added: len(batch)` (`api/ko-routes.go:181`–`api/ko-routes.go:252`). Atomic batch insertion does not make retries idempotent. Probe: identical activity twice creates two IDs, credits 120 rather than 60 seconds and twice the fraction; aggregate SQL sums both (`database/document_user_statistics.sql:10`–`database/document_user_statistics.sql:12`). Do not delete/deduplicate historical server rows heuristically.
- Progress primary key is **(user, document, device)**, not one row per document or an event log. `INSERT OR REPLACE` omits `created_at`, so every receipt generates a new timestamp, discarding that device's prior row. Latest-document lookup sorts only descending `created_at` (`database/schema.sql:77`–`database/schema.sql:90`; `database/query.sql:152`–`database/query.sql:164`; `database/query.sql:322`–`database/query.sql:331`). Timestamp default is second-resolution. There is no client ordering, monotonic revision, compare-and-swap, or deterministic tie rule. Probe confirms stale lower progress takes precedence when replayed later, same-device replacement retains one row, and two devices can tie. Lower percentage is not itself an error: intentionally rereading/backtracking is valid.
- Device IDs are globally unique, not `(user,id)`; `UpsertDevice` changes name/last sync but **not owner** on collision (`database/schema.sql:64`–`database/schema.sql:74`; `database/query.sql:352`–`database/query.sql:359`). Ordinary progress/activity foreign keys verify device existence, not matching ownership. Probe confirms a second user's collision can rename the first user's device and store cross-owner progress. **Proposal:** enforce owner checks in shared operations and issue fresh browser device identities per account; do not repurpose a KOReader device by default. This requires a separate compatibility review of the current “assume device” capability, not silently removing it.
- `/syncs/activity` returns maximum stored **start_time** for the user/device, not a durable cursor or acknowledgement (`database/query.sql:227`–`database/query.sql:233`; `api/ko-routes.go:280`–`api/ko-routes.go:304`). Plugin asks for `start_time > last_sync`, ordered ascending, limit 5000 (`client/syncninja.koplugin/main.lua:73`–`client/syncninja.koplugin/main.lua:85`, `client/syncninja.koplugin/main.lua:622`–`client/syncninja.koplugin/main.lua:650`, `client/syncninja.koplugin/main.lua:977`–`client/syncninja.koplugin/main.lua:1002`). Equal timestamps at a batch boundary, out-of-order arrival, and future clock skew are not safely addressed by that watermark. Preserve this existing wire behavior for the plugin; do not use it to acknowledge the new web outbox.
- KO request structs do not declare range/required constraints for progress/activity numeric fields; ingestion calculates page fractions directly (`api/ko-routes.go:21`–`api/ko-routes.go:50`, `api/ko-routes.go:227`–`api/ko-routes.go:236`). New web validation must define duration/page/fraction bounds and reject invalid/oversized batches, but this evaluation does not authorize changing KO acceptance semantics.

## 4. Proposed target: boundaries, state owners, and invariants

This describes a possible end state, not an implementation sequence. No compatibility wrapper around legacy globals/storage is required.

### React extraction and lifecycle rules

- **Reuse candidate:** engine parsing/rendition operations, KO conversion intent, theme assets, and CFI-range logic after fixtures prove them. **Replace:** application DOM queries, `window.currentReader`, device modal coupling, direct fetch/IDB calls, inline activity policy, global settings, SW message globals, and implicit resource caching. Internal EPUB.js fields (`manager.visible`, `views().container`, `spineItems`, section `wordCount`) stay inside one pinned adapter (`assets/reader/index.js:956`–`assets/reader/index.js:974`, `assets/reader/index.js:1215`–`assets/reader/index.js:1240`).
- The host ref is engine-exclusive; React never reconciles its children. An effect creates one session and disposes it on book/account/route changes; React Strict Mode create→dispose→create must not create duplicate telemetry/listeners. An engine generation/cancellation token suppresses late `book.ready`, section loads, metadata, and location callbacks after disposal.
- Dispose invalidates commands, unregisters hooks/events, removes outer/iframe listeners, cancels timers/debounces, releases wake lock/video, destroys rendition/book, restores owned global theme state, and revokes all application-created object URLs only after consumers finish. Existing local metadata extraction destroys the book while returning its cover URL, and application file URLs are not revoked (`assets/local/index.js:238`–`assets/local/index.js:283`); qualify cover lifetime rather than retaining these assumptions.
- Serialize next/back/TOC/restore/theme reflow; a settled location event drives checkpoints and React status, not a control-specific afterthought. Resize/orientation/font changes restore the logical anchor and must not independently credit activity. Test spread/RTL/section changes and selection/internal/external links so page-turn hot zones do not consume content interactions.
- Native wake lock is an injected optional capability, requested through deliberate user action, released on hidden/dispose, reacquired on visible only with user policy. **Unverified current wiring:** iframe code dispatches `wakelock` on the iframe document, while its listener is on the outer document (`assets/reader/index.js:283`, `assets/reader/index.js:551`–`assets/reader/index.js:558`); a custom DOM event does not cross iframe document boundaries automatically.

### Storage alternatives

**Ideal (recommended):** one versioned IndexedDB repository for book blobs, metadata, account-linked downloads, local checkpoints, events, receipts, and replay leases; Cache Storage only for public app assets. An import/download is `staging → validated → available` with a completion transaction; no published availability before full bytes and required metadata exist. Store resource kind, owning server/account, server document ID, byte/version fingerprint, size, and last verified status. At open, verify bytes still exist and are usable; recover orphan staging entries after crashes. Keep at least the original EPUB exportable for local-only recovery. Avoid a second storage technology unless measurements justify it.

**Pragmatic:** IndexedDB owns records/checkpoints/outbox; explicitly managed, account/version-keyed Cache Storage holds large EPUB bytes. A completion marker follows awaited verified cache writes; startup/open reconciles marker versus byte presence, and deletion is recoverable across the two stores. This is not an atomic cross-store transaction. It can converge on the ideal by moving byte backing behind the same repository interface. Never infer availability by cache URL enumeration or treat browser HTTP cache as durable book storage.

**Invariants:** durable commit before “saved”; one owner per record kind; no account-mismatched replay; no partial download labeled offline; removing cached bytes does not silently remove pending events or server records; unavailable/evicted local bytes are reported honestly. `navigator.storage.persist()` and estimates are advisory, not a guarantee against user clearing/OS eviction. Queue storage failures stop claiming durability and offer explicit recovery/export; automatic quota eviction must not delete unsent events or local-only originals.

## 5. Reliable outbox, deduplication, and conflict alternatives

### Shared minimum browser contract

- Every accepted event receives immutable identity, account/server/installation/device/document namespace, creation/checkpoint sequence, and payload. Persist event plus local resume checkpoint in one transaction before showing saved. Local-only checkpoints never enter server replay; local activity persistence is a separate product choice.
- Replay uses a transactionally claimed expiring lease/fencing generation per account. Web Locks/BroadcastChannel may improve coordination but cannot be the only correctness mechanism. An expired lease may cause duplicate sends; server dedup must still make credit safe. Producer appends and acknowledgement transactions operate on exact immutable IDs, not “delete ACTIVITY” or “delete latest progress key.”
- Retry uses bounded exponential backoff/jitter and startup/foreground/reconnect triggers. `navigator.onLine` is only a hint. Timeouts and lost responses leave the same request pending. Validate HTTP success, media type, schema, account context, and acknowledged IDs. 401/403 pauses for the correct account/re-auth; 409/412 exposes conflict; 429/5xx/network failures retry; invalid/deleted-document/content-version events are retained in a visible blocked state until corrected/discarded explicitly. No successful-JSON parsing shortcut.
- New cookie-authenticated web mutation endpoints need explicit CSRF/origin protection and machine-readable auth failures; credentialed book markup must not bypass that boundary. Existing cookies use configurable Secure/HttpOnly and SameSite Strict (`api/api.go:93`–`api/api.go:100`), which is not a complete new-API authorization/CSRF design. Preserve KO/OPDS credential contracts independently.
- Mutable latest progress may coalesce only **before** assignment to a frozen request, with local sequence protection and no outstanding uncertain acknowledgement. Activity intervals are append-only: rereading the same words is legitimate and cannot be deduplicated by position/time equality. A terminal server rejection is not an implicit user discard.

### Server alternatives grounded in existing tables

| Option | Required additive semantics | Advantages / limits |
| --- | --- | --- |
| **Ideal: per-event receipts + progress revision/head** | Add unique `(user_id, installation_id, event_id)` receipt identity with payload digest, committed result, type, and progress outcome; atomic receipt+activity insert or receipt+versioned progress update. Optional nullable unique event identity on new activity rows is another implementation, but progress still needs a durable receipt after its replaceable row changes. Add per-user/document monotonic head/revision and device sequence tracking. | At-least-once sends, exactly-once credit for identified new web events; safe per-event partial acknowledgement and batching. Historical activity/progress rows remain intact and need no fabricated identities. Repeated key/different payload is rejected. Receipts must be checked before conflict validation on retry so a previously committed event returns its original acknowledgement. |
| **Pragmatic: immutable batch receipts + same progress revision contract** | Add unique account/installation/batch receipt with digest and original result. Browser transaction permanently assigns each activity to one frozen batch before any send; retry exact bytes/IDs, never split/rebatch uncertain submissions. Activity insert and receipt commit in the existing transaction style. Progress gets its own frozen request identity and atomic receipt+revision update. | Fewer server/UI cases, all-or-nothing bounded batches; no per-item salvage of a malformed batch. Atomic browser assignment/ack prevents accidental overlap. Can evolve to per-event receipts without abandoning already submitted batch identities. Still requires an additive server ledger and progress participation by every writer. |

**Not reliable alternatives:** client-only retry/deletion, a receipt written separately from activity, “exactly once” networking, latest start-time watermark, heuristic unique `(device, start_time)`, max-percentage-wins, client-wall-clock last-writer-wins, or a web-only revision counter that ignores KO writes. The existing schema cannot distinguish a legitimate identical activity from a resend. No browser package can manufacture that information after the fact.

Receipts must outlive the supported offline retry lifetime; indefinite pending events require retained receipts or explicit installation retirement that rejects old IDs, not silent TTL expiry followed by duplicate acceptance. Store payload digests/outcomes rather than logging EPUB text or full reading payloads. Define account deletion/backup/restore/rollback handling for added tables (existing user deletion uses an explicit trigger, so new receipt/head foreign keys require compatible cascade/trigger cleanup: `database/schema.sql:194`–`database/schema.sql:200`); restoring activity without its dedup ledger reopens duplicate-credit risk. No historical server deduplication or destructive schema rewrite is proposed.

### Progress conflict policy: choice required

**Ideal:** compare-and-swap against a monotonic user/document revision shared by web and KO writes. The versioned head exposes the selected KO path/fraction/device and deterministic order; per-device historical current rows remain available. A new web request sends `base_revision` and local sequence; if unchanged it commits the new path (including backward moves), increments revision, and stores receipt atomically. If advanced elsewhere, store/return an explicit conflict with local and remote positions. Allow “continue here” to publish a new intentional event against the current revision, or “use other device” to retain/discard the local candidate explicitly. Do not replay later events past a blocked predecessor without a defined rebase.

KO request/response shapes remain unchanged. Its unconditional writes continue to act as new receipt-ordered progress, while shared server operations atomically advance the internal revision/head so stale web replay cannot miss them. KO reads must see the same selected progress, and web conflicts must see KO updates. Bootstrap heads from existing rows without deleting or rewriting history; same-second historical ties have no recorded winner, so a deterministic tie rule needs approval. SQL statistics selection and any direct progress writers must agree with the new canonical ordering. Merely adding `revision` to web DTOs while leaving `GetDocumentProgress` and KO writes untouched is insufficient.

**Pragmatic:** the same atomic revisions/receipts, but **never automatically overwrite an advanced head**. Quarantine all stale progress and present a simple local-versus-server resume choice on foreground/open; activities can synchronize independently. Initially allow one outstanding progress request per account/document, no automatic merge or speculative rebasing. This avoids sophisticated reconciliation and can evolve to the ideal UX. Both options preserve backward movement; neither guarantees event-time ordering for legacy KO clients that send no event identity/time. That residual KO limitation must be stated, not claimed solved by a new web contract.

Device identities should be account-specific and new by default. If “assume existing device” remains, require same-account authorization, quiescence/ownership semantics, and sequence-generation handling so two installations cannot impersonate one ordered writer. “Fix progress by timestamp” is not safe: seconds can tie and clocks can skew. “Keep highest fraction” rejects legitimate backtracking.

## 6. EPUB content security

**Confirmed configuration:** `allowScriptedContent: true` is supplied by the custom reader (`assets/reader/index.js:145`–`assets/reader/index.js:152`). The bundled engine creates `sandbox="allow-same-origin"` and adds `allow-scripts` under that option; it defaults to `srcdoc` when supported and also has blob/write paths (`assets/lib/epub.min.js:1`). The comment that disabling scripts simply sets a sandbox is incomplete: a sandbox is present in both cases, with materially different permissions.

The custom hook appends a CSP meta to the parsed chapter head with script-src none, object-src none, style rules, and Trusted Types requirement (`assets/reader/index.js:333`–`assets/reader/index.js:361`). This is **not proof of isolation**:

- A meta appended after original head content cannot retroactively protect earlier parser-executed scripts/resources when serialized chapter content is loaded. Actual engine hook/serialization/load ordering must be tested across srcdoc/blob/write paths.
- Same-origin plus script permission gives malicious content a route to application-origin capabilities if script execution occurs before/around the intended restriction. React escaping app metadata does not secure EPUB iframe markup.
- No default-src, connect-src, img-src, font-src, frame-src, base-uri, or form-action restrictions are set there. Remote resource loads/CSS URLs, nested frames, forms, and navigation need independent policy. Trusted Types is not portable sanitization and cannot be relied on for script-free EPUB content.
- The browser import check only looks for PK and two text substrings; it neither proves an EPUB structure nor enforces expansion/resource budgets (`assets/local/index.js:291`–`assets/local/index.js:319`). Server archive validation has actual file/entry/expansion/count/text limits, but local import bypasses it (`metadata/archive.go:21`–`metadata/archive.go:28`, `metadata/archive.go:133`–`metadata/archive.go:153`; `metadata/epub.go:73`–`metadata/epub.go:106`). Server ZIP validation is not HTML sanitization either.

**Ideal:** run untrusted content in a genuinely separate origin/opaque sandbox with no application credentials/storage and scripts disabled, under restrictive response-level CSP and a small validated communication protocol. A trusted renderer/bridge must not grant book script execution or general parent RPC. This may require a different engine integration because current parent-side CFI/DOM access relies on same-origin content. Evaluate offline resource routing and theme/position fidelity before selecting this boundary; do not assume EPUB.js can be switched to opaque origin without redesign.

**Pragmatic:** retain parent DOM access only with EPUB scripts disabled (`allow-same-origin`, **without** `allow-scripts`), sanitized chapter markup/resource URLs before serialization, restrictive policy placed before content parsing, explicit resource allowlist and external-link handling. Prove contemporary Safari listeners/CFI behavior instead of retaining a historical workaround by assertion. This is a weaker isolation boundary than separate origin, not a waiver of script/network tests. If required platform behavior only works with scripts enabled, do not silently fall back to the present unsafe combination; fail the proof and revisit the engine boundary.

Both options need bounded archive parsing (size/entries/expanded bytes/ratio/CRC/structure), safe URL resolution, no unintended network or authenticated same-origin requests from book markup, control of script/event-handler/javascript URL/SVG/form/frame/base/meta-refresh behaviors, and explicit handling of DRM/unsupported files. Preserve original bytes/export and the DOM-to-position relationship: sanitization that changes element/spine structure can invalidate KO positions, so test compatibility against the original document or maintain a mapping. Reader content must not be passed to React `dangerouslySetInnerHTML`. External links require user intent and safe opener handling. Inventory/pin/hash bundled dependency versions before reuse; no unsupported version or CVE conclusion is inferred from the minified files.

## 7. Mobile/platform and account behavior

### Proposed required platform behavior

- **Offline restart:** installed app launches its local shell without login/network, resolves book records and last local checkpoint, and reopens downloaded server/local-only EPUBs after full process termination. A previously open iframe in airplane mode is not evidence. A first-ever never-cached launch cannot be offline; present installation/download readiness honestly.
- **Storage:** detect failed/blocked IDB opening/upgrades, private-mode quota constraints, Cache Storage/SW absence, partial eviction, and user-cleared data. Give actionable storage errors; no persistent-storage promise beyond platform guarantees. Local originals need export/re-import guidance; downloaded server bytes can be reacquired, unsent events cannot be casually evicted.
- **iOS/Safari installed and tab modes:** physical tests for safe areas on all edges/orientations, browser chrome/keyboard dynamic viewport, screen lock/app switch/OS kill, file picker/import/export, audio interruption, and wake-lock permission/lifetime. Historical NoSleep comments mention iOS 17.03, not a supported-browser decision (`assets/reader/index.js:253`–`assets/reader/index.js:268`). Do not require media playback to read.
- **Android/Chromium and desktop:** equivalent restart/update/quota cases, install behavior, font load/reflow, split screen/orientation, keyboard and selection, large EPUB decode/turn latency. Background Sync, Periodic Sync, Wake Lock, and installed-app storage behavior must each be feature-detected; correctness cannot depend on them.
- **Accessibility:** allow pinch/browser zoom (current pages disable user scaling: `assets/reader/index.htm:5`–`assets/reader/index.htm:8`; `assets/local/index.htm:5`–`assets/local/index.htm:8`); use semantic named buttons, focusable TOC, focus-managed modal/panels, visible controls as alternatives to gestures, large text/contrast/reduced motion, screen-reader traversal through frame/chapter changes, and adequate touch targets. Keyboard shortcuts must not steal input while typing or selecting text. Do not preserve hidden checkbox/label/modal or SVG-only interaction internals as contracts.
- **Performance:** current code parses every local book for covers on every listing and all spine sections concurrently at open (`assets/local/index.js:52`–`assets/local/index.js:56`, `assets/local/index.js:238`–`assets/local/index.js:283`; `assets/reader/index.js:1316`–`assets/reader/index.js:1327`). Propose bounded parsing concurrency, persisted validated derived metadata, cancellation, and measured memory/latency budgets. No timing/device-memory result exists yet. Image-heavy, long-spine, non-Latin, RTL, fixed-layout, malformed, and zero-text books need synthetic fixtures.

### Logout/account alternatives — approval required

**Ideal:** explicit “keep downloads on this device” choice with visible owner/account; server-linked data is hidden/locked to that account, pending events remain paused until that exact account authenticates again. Logout with unsent data explains retention/discard, never submits it as a new user. Local-only books remain separately available without an account. Browser account scoping is not encryption or a defense against another person with access to the same browser profile; state that threat-model limit.

**Pragmatic:** remove server-linked downloaded bytes at explicit logout, but retain account-scoped pending events in a locked/paused namespace until same-account re-auth or explicit discard; retain independent local-only books. Account switch stops/invalidates in-flight coordination and checks identity again before acknowledgement. This is simpler shared-device behavior and can later add the retention choice. Neither option deletes server progress/activity/files. If policy instead requires clearing pending events on logout, obtain explicit loss-of-unsent-data approval; do not implement it as cleanup.

## 8. Retiring stale root-scoped service workers

Legacy browser books, pending events, caches, and preferences may be discarded. **Server data, KO/OPDS routes, and data created by the new frontend may not.** No old-key adapters or browser data migrations are proposed.

### Ideal: replacement at the existing registration identity

A new root worker remains served at **`/sw.js`**, on the same origin/scope, with valid JavaScript MIME, revalidation-oriented headers and no auth redirect/SPA fallback. It recognizes a one-time legacy-reset epoch, activates/claims deliberately, removes known legacy caches (`OFFLINE_V1`) and triggers controlled reload of old clients into a complete new shell. New app asset caches use their own versioned namespace, immutable hashed assets, and a navigation-only shell fallback; private API/protocol/binary failures never become shell HTML. Activation/reset ownership is serialized; new app storage is never reset by repeated startup or another tab.

The bootstrap handles old IDB deletion (`keyval-store`) and `readerSettings` removal with blocked/open-tab recovery. Cleanup is scoped to known AnthoLume names; do not copy the legacy all-origin purge. Stale cached `/assets/common.js` must not get an opportunity to reinstall the legacy worker indefinitely; the old `/sw.js` URL must keep serving the new retirement/replacement behavior for long-absent clients. Keep manifest identity intentional (explicitly preserve inferred `/` identity if appropriate), independent of storage reset.

**Risk requiring proof:** existing cache-first shell can initially serve old scripts even while a new worker installs. Multiple old reader tabs may still hold events in memory and recreate deleted keys or attempt legacy replay. Claim/reload must retire those clients, not just delete a cache. Consider a narrowly scoped transition-worker block for obsolete controlled-browser mutation requests while replacing their pages; it must not alter server KO/OPDS contracts or affect external clients. Already accepted/in-flight server requests cannot be erased by a browser reset. Do not promise an atomic purge of activity already delivered to the server.

### Pragmatic: bounded tombstone worker, then new shell worker

Serve a tiny retirement worker at `/sw.js` that explicitly activates/claims, awaits deletion of known legacy caches, retires old clients, and directs online clients to fresh bootstrap. If it unregisters, ensure old controlled pages cannot simply re-register old cached scripts and ensure a complete successor shell exists before claiming offline availability. The successor can use the same registration URL to avoid a registration gap. Handle blocked IDB deletion in page bootstrap; a SW cannot clear localStorage. Keep the tombstone/replacement response available at the old script URL; a 404, redirect, or deletion of the source file alone is not a reliable retirement mechanism.

This can evolve to the ideal managed-update worker, but adds handoff/offline-gap testing. **Recommended:** use the replacement-at-same-URL option unless a proof shows the tombstone materially simplifies deployment. Immediate skip-wait/forced reload is acceptable for the explicitly disposable **legacy** state; future app updates must preserve new outbox/book data, use versioned browser/API schemas, and coordinate active reading rather than reset it.

No solution updates a device that never reconnects or prevents all old rendering before its first successful update check. Define cutover guarantees as **after a successful online retirement check and controlled reload**; an offline legacy launch can remain old until then. Do not claim origin-wide `Clear-Site-Data` is the default: it can clear unrelated storage/cookies, has platform differences, and does not replace worker/client lifecycle handling.
