# M2 — API/schema contract proof

**Schema-first strict Gin is viable for the bounded operations tested; this is not production migration or full API parity.** The authorized M2 proof lives in [`prototypes/api-contract`](../../prototypes/api-contract/README.md). No production handlers, dependencies, schema, git state, or private snapshot were changed/accessed by this work.

## Architecture and scope

Authority: the migration design, approved M1 architecture/workflow evaluations, and the user's M2 authorization, including autonomous selection of conservative explicit progress conflicts. The parent records M1 approved/M2 in progress; this report covers only the bounded API proof, not the overall M2 exit gate.

| Boundary | Current production structure | Proof target / owner |
| --- | --- | --- |
| HTTP | Gin handlers mix queries, DTOs/templates, and writes (`api/api.go`, `api/ko-routes.go`) | Reviewed OpenAPI → generated strict Gin interfaces; `server.go` owns authentication, CSRF, limits, parsing, DTO mapping and safe problems |
| Reading writes | SQLC writes have no web event receipt or shared revision | `store.go` is the single transaction owner for effect + immutable receipt; KO-style operation uses the same revision advance |
| Persistent state | Existing SQLite core tables (`database/schema.sql`) | File-backed WAL fixture; actual root SQLC `GetDocument` and `UpdateProgress` through local module replace; additive `proof_receipts` and `proof_heads` only in fixture |
| Client | Ad hoc JS HTTP contracts | Generated TypeScript + `openapi-fetch`; typed nullable/error/binary use and a narrow runtime acknowledgement predicate |

Dependency direction: generated HTTP adapter → SQLite operations / root SQLC. No handler calls a production HTTP adapter. The proof keeps transport and operations in separate files in one small package; operations still use generated DTO/result shapes. Before promotion, keep generated types at the HTTP boundary and map transport-independent inputs/results explicitly. This proof does not introduce a production service/repository hierarchy.

**Ideal:** promote reviewed contracts through shared operations, real additive migrations, file publication, full compatibility and browser tests. **Pragmatic:** retain this discardable module as evidence, then implement the same contracts in the authorized vertical slice. No runtime bridge or second production API is introduced.

## Chosen contracts

- Six representative operations only: paginated documents, EPUB download, validation-only multipart upload, progress event, activity event, administrator probe. The shared library remains shared. Lists use stable ID order, identical count/deleted filters, required nullable title/author, non-null arrays and nullable `next_page`. Offset paging makes no cross-request snapshot promise; count/items share one transaction.
- Signed fixture session cookies are Secure/HttpOnly/SameSite Strict. The principal and current administrator flag come from SQLite on each request, never client JSON/session role. Anonymous, bad signature and nonexistent-account cookies return 401; nonadmin/currently demoted admin gets 403. Credential login/bootstrap, real auth-hash revocation and session-expiry timing are not proved.
- Unsafe requests require the session-bound fixture token and one exact configured origin, including multipart. `NewRouter` retains `https://proof.invalid`; `NewRouterWithOrigin` validates one HTTP(S) origin without wildcard/credentials/path/query/fragment. The later browser integration supplies its actual test listener origin, never rewrites request Origin, and uses the same auth/CSRF/validator stack. Authentication/authorization and byte limits precede schema validation. Validator authentication verifies the existing principal rather than accepting security declarations unconditionally.
- All handled errors use safe `application/problem+json` `{type,title,status,code,detail,current_revision?}`. Parse, schema and known-field semantic errors are deliberately **400**, not 422; auth 401, role/CSRF 403, missing download 404, revision/identity conflicts 409, bytes 413, media 415, storage 500. This chooses the architecture evaluation's problem-envelope proposal over the workflow report's alternative nested `error` envelope.
- JSON bodies are capped at **8,192 bytes**, including chunked/unknown-length transfer. Schema rejects unknown/wrong-case fields, null/missing required values, invalid dates/revisions, nonfinite/out-of-range fractions and oversized strings. A separate bounded recursive token pass rejects duplicate names, including escaped equivalents. Body replacement occurs **before** middleware validation; the generated strict binder consumes the retained validated value.
- Activity and progress have separate immutable event identities, scoped by account and shared across operation kinds. Hash identity includes the kind and normalized typed payload; JSON order/whitespace/numeric spelling (including positive/negative zero in all three fraction fields) and equivalent timestamp offsets do not change identity within the parsed float64 representation. Fractions use generated `float64`, revisions opaque decimal strings, positions opaque unchanged KO XPath. Activity duration is 0–86,400 seconds; end fraction must not precede start. This is delivery validation, not a new activity-measurement/WPM policy.
- A transaction commits each effect and its receipt together. Exact retry returns the original receipt, with no new activity or revision, even after later writes or DB close/reopen. Same ID with changed payload/kind returns `idempotency_conflict`. Owned existing devices and live documents are checked before new effects; invalid writes create no device/document placeholders.
- Progress uses a document/account CAS head, starting at revision `"0"`. Valid backward moves advance it. A stale write returns durable `progress_conflict` with the revision observed at that decision; retry returns that original conflict even if the head later changes. Rejected CAS events are receipted, not silently rebased. Explicit local resolution uses a **new event ID and freshly observed base revision**. Old accepted receipts remain acknowledgements, not current reading-state responses.
- An accepted KO-style unconditional operation advances that same head and writes the actual legacy per-device SQLC row, without inventing a web receipt or requiring web CSRF/event IDs. A test-only HTTP shim invokes this operation; exact KO-device fraction/position, absence of web receipts, and legacy-row failure rollback are asserted. This proves operation-level coexistence, **not** the real KO HTTP/auth/GET integration. Activities can be credited independently of progress conflict.

The new fixture HTTP tests exercise actual Gin/session libraries at the selected versions.

## Proved versus pending

**Proved:** the concrete graph compiles; strict generation/retained validation works; negative validation and response-contract checks detect faults; bounded synthetic binary paths work; account-scoped durable receipt/CAS semantics survive duplicate delivery, failed receipt commit, lost HTTP response and SQLite reopen.

**Not proved / required before promotion:**

1. Production migrations/backfill and old/new populated DB upgrades. The precise fixture includes all document columns used by actual SQLC and relevant core foreign keys, but omits production migrations, statistics, triggers and unrelated user/device columns. No snapshot or production data was used. Close/reopen is not a process/power-loss or disk-full qualification.
2. A real shared reading-state read and KO/OPDS protocol fixtures. Existing receipt-time reads have same-second tie ambiguity; promotion must tie authoritative current state to the shared revision, not infer it from percentage or ambiguous legacy timestamp sorting. The sidecar here proves revision participation, not production read integration. Every production writer must participate before CAS guarantees apply; old-binary downgrade needs gating.
3. Durable upload/publication and collision/tombstone repair. Upload is explicitly **`validated_only`**, not 201 or a managed file write. ZIP signature/mimetype, path and decompression limits are a bounded acceptance harness, not complete EPUB validation/content safety. Synthetic archive has no EPUB conformance certification.
4. Large-file streaming/RSS ceilings, slow/interrupted transfers, active download/upload cancellation, Range/206/416, ETag/304, reverse-proxy behavior and custom imported paths. Download uses a small bounded in-memory fixture; upload buffers at most 69,632 wire bytes before validation, at most 65,536 file bytes, at most 131,072 expanded bytes and 32 ZIP entries. Part-header bytes count against the wire ceiling; outer HTTP header/connection limits remain deployment/server work. Post-header transport failures cannot become a fresh JSON problem.
5. Real credential/session issuance/revocation/expiry/rotation, rate limits, production cookie keys, proxy/origin configuration and fresh administrator authentication. Fixture bootstrap is test-only, and fixed fixture tokens are not a production token-issuance design.
6. Production browser outbox, complete client response validation, installed-PWA behavior and conflict UI remain pending. The original TS runtime tests here use mock fetch. The later [browser/Go integration proof](m2-integration.md) now composes the actual sibling Repository/SyncCoordinator/runtime receipt gate with these generated bindings, signed fixture cookies/CSRF and SQLite operations over actual Chromium HTTP, including lost response/reopen and real CAS conflicts. That bounded socket evidence does not supply production auth, SW or a complete resolution UI. Generated types alone still do not validate unknown runtime JSON; the narrow API acknowledgement predicate alone is not an outbox implementation.
7. Receipt retention/capacity, canonical payload versioning, observation-time persistence beyond digest identity, revision exhaustion, multi-process SQLite contention/retry policy, audit/maintenance/account deletion and recovery. This proof retains receipts indefinitely, uses a one-connection operation owner, and reports generic storage errors rather than a production busy/maintenance policy. Client observation clocks do not order progress.

### Task-end report

- **Assumptions:** shared-library policy persists; proof-local numeric ceilings are evaluation values, not deployment limits; a full repository checkout is available for the local SQLC replacement.
- **Autonomous decisions:** problem envelope and validation 400; durable CAS rejection receipts/new-ID resolution; decimal revisions, UTC/signed-zero-normalized identity, separate receipts, fixture-only schema/upload; patched compatible x/crypto 0.59.0 and isolated SHA-verified Go 1.26.11 for review verification.
- **Compromises:** no production migration/auth/KO adapter or durable file publication, because this is a bounded proof; [fixture TS/browser socket composition is now accepted](m2-integration.md#independent-acceptance), while production and large-stream/range/cancellation qualification remain separate gates.

**Knowledge capture:** before promotion, capture strict-Gin request-context unwrapping, pre-validator limits/duplicate scanning, retained validated-value ordering, and top-level generator remote-ref policy in the web API package's `AGENTS.md` or generation README. Keep these executable checks beside that boundary, not global agent guidance. KO-device row/rollback and signed-zero/CRC mutants are now retained in this proof's tests and fault script.
