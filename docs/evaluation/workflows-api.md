# M1 — Web Workflows and React API Contracts

## Evaluation Result and Authority

The existing server supports a shared library, user-scoped reading records, local-only reading, external acquisition, and privileged filesystem/database administration. A React replacement needs an intentional API for all of these, not JSON versions of template variables. The highest-risk boundaries are session revocation, shared-library authorization, reading-event acknowledgement/conflicts, statistics freshness/timezones, and destructive restore.

**Evidence status:** static source evaluation only. “Confirmed” below means observed in source, not exercised against a running deployment. No snapshot, live database, private logs, external provider, or browser profile was accessed. No build, test, browser, backup, or restore was executed. Acceptance cases below are specifications, not passing test claims. This report does not complete the M1 runtime gate.

**Approved constraints:** ground-up React redesign; preserve server databases/files and KOReader/OPDS compatibility; no legacy browser-data compatibility. Implementation and the detailed behavior changes below remain unapproved. Authority: `docs/frontend-migration.md:5`, `docs/frontend-migration.md:13`, `docs/frontend-migration.md:169`, `docs/frontend-migration.md:282`.

Two implementation choices, neither a permanent dual frontend:

- **Ideal — recommended target:** versioned web API, explicit DTOs, shared application operations only where business rules are shared, durable acknowledged reading synchronization, observable long-running operations, and safe administrative recovery. React receives domain data rather than HTML, chart paths, or SQLC rows.
- **Pragmatic — same destination:** prove one authenticated read, one idempotent reading mutation, one binary transfer, and one job/status operation before expanding coverage. Keep existing persistence/supporting packages and external adapters; add only necessary server migrations. This is a narrower proof, not permission to omit admin/offline capabilities or ship unsafe acknowledgement/restore behavior. SSR responses are not an API bridge.

### Proposed invariants and validation ownership

These are target guarantees, not facts asserted to hold in the current implementation:

- **Authorization and isolation:** current account/role authorizes every protected operation; raw reading records and replay are account-scoped, global books remain shared under approved permissions. Owner: auth/application operations and browser sync; T02/T05/T08/T22/T25.
- **Durability and idempotence:** saved local events are durable before reporting success, and credit occurs once per accepted v1 event identity; acknowledgements name committed events. Owner: browser persistence and reading-write transaction; T29/T31.
- **Ordering:** server revisions arbitrate web progress conflicts, including accepted KO writes; intentional backward progress is valid. Owner: progress application operation; T26/T29/T42.
- **File identity and compatibility:** stored server IDs, KO position strings, existing bytes and valid external basepaths survive API/UI replacement. Owner: document admission/persistence and protocol adapters; T13/T15/T17/T26/T42–T44.
- **Recovery and derived state:** destructive jobs require validated recovery state; statistics expose coherent generation/freshness and never masquerade as authoritative raw progress. Owner: admin executor/statistics; T11/T24/T35/T38–T40.
- **Single ownership:** React controls, engine DOM, outbox replay, and job execution each have one explicit owner; unmount/restart/account-switch cannot leave competing writers. Owner: browser controller/sync and server executor; T05/T21/T27/T29/T31/T40.

## 2. Reading the Capability Matrix

Actors: **P** public/unauthenticated; **U** authenticated web user; **A** authenticated administrator; **K** KO-compatible authenticated client; **O** OPDS Basic-authenticated client; **L** local browser user, no server account required.

Current common conditions:

- Web **U/A** failures redirect to `/login` (302); non-admin admin access renders 401 HTML. Most handler/storage failures are HTML 400/404/500 and sometimes contain internal error text. Reader JSON routes inherit these redirects/HTML errors (`api/auth.go:115`, `api/auth.go:130`, `api/app-routes.go:1028`).
- No document ownership ACL exists: any **U** can read/edit/delete the same global library; only activity/progress/preferences are user-scoped (`database/schema.sql:18`, `database/query.sql:182`, `api/api.go:151`, `api/api.go:177`). Admin is not required for ordinary uploads/metadata/acquisition.
- **D** means blocked by demo route substitution with 401; **R** registration flag; **S** external-search flag. No marker means no explicit feature gate at that route. Cookie/configuration details are in §3.
- Unless explicitly stated, there is no user-selectable sort, additional filter, pagination, or offline server operation. Browser cache availability is not guaranteed by a successful server page response. Proposed API operations are in §8 and acceptance IDs in §10.

### Proposed web authentication contract

- Web API accepts cookie authentication, not KO digest headers as a second web identity. Missing/expired/revoked session is JSON 401, insufficient role 403; no login HTML/302 for `/api/v1` or missing binary resources.

## 4. Document, Metadata, and Acquisition Semantics

### Confirmed subtleties

1. **Identity is not a new UUID for server books.** New server EPUB IDs derive from the KO partial-MD5 algorithm; full MD5 is a separate field. Existing IDs can be arbitrary strings inserted through compatibility routes. Preserve stored IDs exactly, do not impose a new 32-hex invariant over old data. A digest/partial digest is a compatibility key, not an authorization credential or collision-proof content identity (`utils/utils.go:12`, `metadata/metadata.go:101`, `api/ko-routes.go:306`).
2. **Shared library, per-user statistics.** Deleting affects all users and sends KO tombstones, while raw history remains. Direct detail/download/cover paths ignore `deleted`. Duplicate uploads/imports do not resurrect or fill existing rows. This makes “delete”, “remove download”, “delete local book”, and “purge bytes” four distinct concepts; only the first three are current workflows (`database/query.sql:36`, `database/query.sql:126`, `api/common.go:15`, `assets/local/index.js:73`).
3. **Metadata preview is already a server mutation.** Both identify and automatic cover lookup insert first-result metadata; application overwrites selected document fields via form input. There is no current routed proposal-history/revert/batch-match feature. Open Library source is unimplemented through `SearchMetadata`; unused supporting helpers do not create parity requirements (`api/app-routes.go:694`, `api/common.go:131`, `metadata/metadata.go:63`, `api/app-admin-routes.go:109`).
4. **Read-triggered provider work reveals library metadata.** Cover GETs send title/author to Google and persist a failure sentinel; preview image is fetched directly from Google by browser. This happens independently of acquisition/search configuration. Google calls use default `http.Get` without explicit timeout; cover writes do not validate HTTP status or size and create the file before successful download (`api/common.go:109`, `templates/components/metadata.tmpl:46`, `metadata/gbooks.go:121`, `metadata/gbooks.go:158`).
5. **External acquisition is blocking network/file work.** Search pages have a 10-second client timeout but no status validation; book downloader disables TLS verification, has no overall timeout/size bound at transfer, and does not close response body here. Metadata validation after download is too late to bound transferred bytes. Parsed remote links/redirects need destination restrictions. Invalid HTML can cause parser indexing errors; fallback only occurs on returned errors, not semantically empty results (`search/search.go:96`, `search/search.go:119`, `search/libgen.go:50`, `search/downloaders.go:36`).
6. **File admission safety is stronger than old UI hints.** Server EPUB checks cap file 64 MiB, entries 10,000, entry expansion 64 MiB, total expansion 256 MiB, ratio 1000, text item 8 MiB, central directory 16 MiB; validates duplicate entries, container/rootfiles and bounded expanded reads/CRCs. The browser heuristic is not an equivalent trust boundary. Cover and restore archives need their own budgets, not assumed reuse of EPUB rules (`metadata/archive.go:21`, `metadata/archive.go:85`, `metadata/archive.go:126`, `metadata/archive.go:149`, `metadata/epub.go:73`).
7. **Words are an estimate, not a transport field to trust.** Server count strips script/style/noscript/iframe and counts text whitespace fields; reader uses `innerText`/split over spine. Their claimed equivalence is not proven, especially empty content and non-whitespace-segmented languages. Document statistics are computed from fraction × document word count, not measured page words stored in activity (`metadata/epub.go:73`, `assets/reader/index.js:1316`, `database/document_user_statistics.sql:105`).

### Proposed domain contract

- `Document` contains stable `id`, nullable title/author/description/ISBNs/series/language/provider IDs where supported, file availability/media type/byte count/content revision, cover state/revision, creation/update instants, deleted state where authorized, and a separate per-user reading summary. No internal absolute `basepath`, `filepath`, hashes used for authentication, or SQLC bookkeeping is exposed. Retain server fields not editable by web; omission cannot erase them.
- Patch semantics: omitted = unchanged; explicit null = clear nullable metadata; empty string either preserved as explicit empty or normalized to null by a documented field policy (D08). Unknown/deleted resource cannot be created by PATCH. Revision precondition prevents silent lost edits. Existing arbitrary IDs remain URL-encoded opaque strings.
- Upload requires bounded EPUB multipart, reports `201 created` or `200 existing` with disposition and document reference; collision/content-mismatch, tombstone and metadata-only repair outcomes must be explicit, not accidental upsert. Persist file through staging/atomic rename and reconcile DB/file failure. Never overwrite another document merely because a derived display filename matches. New migrations must not rewrite existing bytes/IDs.
- Metadata identify returns candidates with source/provider ID and nullable fields; no-result is `200 items:[]`, upstream unavailable/time budget is a typed 502/504. Proposed default: preview does not modify document or history; apply explicitly records provenance and selected fields. Persisting candidate history and multiple selectable candidates extend existing first-result behavior and require D08 approval.
- Cover states include `unresolved`, `available`, `removed`, `not_found`, `missing_file`; return fallback bytes without converting an upstream outage to permanent not-found. Proposed ideal: GET serves known local cover/fallback only; explicit resolution job fetches provider content. Pragmatic proof can retain bounded lazy resolution behind a named policy, with coalescing and observed outcomes; it must be removable without changing the public DTO. Neither path is approved until D07 resolves outbound consent/automation behavior.
- Applying provider metadata with a cover cannot report one undifferentiated success if cover retrieval fails. Proposed apply result reports metadata revision and cover outcome; if atomic all-or-nothing is selected, stage cover first. Choose one in D08; do not recreate silent partial saves.
- Acquisition uses an approved source/result ID, not arbitrary client download URLs. Validate source before job creation, enforce time/size/redirect/TLS/destination budgets, close response bodies, clean rejected temporary files, and reuse the same admission operation as upload/import. Acquisition completion identifies the actual document by its compatible server ID. Retry/double-click must not create duplicate books/jobs unnoticed.

### Proposed admin operation model

- Admission returns a durable job reference before long-running acquisition/import/backup/restore/refresh work. Proposed states: `queued`, `running`, `succeeded`, `partially_succeeded` (import only), `failed`, `cancelled`, `interrupted`. Include stage, completed/total units when known, numeric progress only when meaningful, safe error code, timestamps, result/artifact reference and `retryable`. Reconnect polls by job ID; optional event streaming is an optimization, not required for correctness. Never return success solely because goroutine started.
- The job executor owns context/lifetime, not Gin request context; bounded concurrency and time/storage limits; job/resource authorization checked on every read. Acquisition initiator can observe own job; admins can observe administrative jobs. All mutations recheck capabilities. No arbitrary command/action string executor.
- Pragmatic job proof can have one in-process worker with persisted status and mark unfinished jobs `interrupted` after restart; ideal worker resumes only stages proven idempotent. Neither claims automatic restore restart/resume. Retention, cancellation support and retry windows are D09/D16 decisions; do not invent cancel UI if a destructive stage cannot safely cancel.
- Imports validate known root and relative path, reject out-of-policy symlinks/escape after canonicalization, expose DIRECT vs COPY operational consequences and duplicate handling before starting; returned per-file results are paginated/safe error records, preserving SUCCESS/EXISTS/FAILED capability. DIRECT remains a server compatibility requirement, not a request to copy every historical file.
- Backups use consistent SQLite snapshot mechanics and a manifest distinguishing database, managed covers/books, externally referenced bytes and omissions. Preserve ability to read existing backup formats, but do not reproduce unsafe extraction or flattening in new exports. A DB-only backup remains valid as DB-only, not “complete library”.
- Restore requires fresh administrator authorization, exclusive maintenance/write barrier, bounded staged archive validation (every entry, traversal/absolute paths/symlinks/duplicates/CRC/expansion/schema/files), compatible DB migrations and preview of coverage. Confirm with immutable validation reference before destructive execution; recompute/reject if input changed. Verify rollback artifact durably closed before replacing state. Use configured DB location, retain/rebind intended DIRECT basepaths by explicit policy, reload coherently, invalidate all sessions/cache and expose recovery outcome without leaking restored users.
- A restore invalidates initiating cookie, so job observation must have an intentional post-restore contract: reauthenticate against restored accounts or use a narrowly scoped, expiring operation receipt with no general data access. Proposed default is reauthentication plus operator-visible recovery status; credential/receipt policy requires D16 approval.
- Do not advertise metadata batch matching as implemented. A new matching engine is new scope; capability false until separately approved.

## 8. Proposed `/api/v1` Surface

All entries in this section are **proposals**. Operation names are intended OpenAPI `operationId`s, not current routes. Each capability maps to the matrix and executable acceptance cases. Keeping a smaller proof does not remove any required operation from final coverage.

### Shared wire rules

- Same origin, cookie + CSRF for web unsafe methods. P/U/A scope as above, per-operation checks; no SQLC serialization. JSON `application/json`, binary exact media type, multipart explicitly documented. Dates/units/nulls have one definition. UUID-like event/job/device IDs are opaque strings; server document and username IDs retain legacy identity, not forced into UUID types.
- `fraction` is finite number in `[0,1]`; cumulative `read_fraction` can exceed 1. Percent display is fraction ×100 and never accepted as ambiguous `percentage`. Duration integer seconds ≥0 under a documented event limit; word estimates nullable integer; timestamps RFC3339 UTC; event IDs strings; revisions opaque strings, not client wall-clock ordering.
- List envelope `{items:[],page,page_size,total,next_page}` with no null arrays; page ≥1, page_size 1–100 (proposed), defaults per resource. Stable sort with tie key; total and items use identical authorization/filter/deleted rules. Pagination links/state retain filters. Offset paging has no cross-mutation snapshot guarantee; include collection revision/as-of where required. Opaque cursor paging is an alternative only if the selected UI needs stable long sessions. Do not mix both initially.
- Errors `{error:{code,message,fields?,request_id,retryable}}`, no stack/query/path/credential leakage. 400 parse/query/unknown enum; 401 auth; 403 authorization/feature/demo/CSRF; 404 unknown resource or unavailable optional route as specified; 409 state/idempotency/progress conflict; 412 revision mismatch for metadata; 413 byte/expansion limit; 415 unsupported MIME/type; 422 semantically invalid known fields; 429 rate limit; 500 internal; 502/504 upstream; 503 maintenance/storage/job capacity. Clients never acknowledge mutations based on HTTP success alone: validate expected body and exact event ID/result.
- Proposed disabled known v1 feature: typed 403 `feature_disabled` (rather than absent route); 405 unsupported method; unknown `/api/v1/...` always JSON 404, never SPA. Old protocol paths retain their existing behavior.
- Binary GET checks authorization before headers; documented Content-Type/Length/Disposition, safe filename encoding, private caching/ETag/Last-Modified policy, Range/206/416 and conditional requests. Downloads cache only successfully verified EPUB bytes, not redirected HTML/login/error content. Full-content integrity identifier for offline manifests is not MD5-based authentication.
- Capability response exposes version/API support, registration/acquisition/provider availability, upload limits, allowed operations for current session when authenticated, demo restrictions and timezone options version. It never exposes data/config absolute paths, signing keys or user list. Session and protected responses are private/no-store where appropriate; protected book caching is an explicit account-scoped browser action.
